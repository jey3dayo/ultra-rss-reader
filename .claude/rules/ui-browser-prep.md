# UI ブラウザ確認ルール

## UI/UX 調整の開始手順

- UI の余白、配置、視覚状態を調整する時は、コード変更前に必ずブラウザで実画面を開いて確認する
- 開発サーバーは `mise run app:dev:browser` で起動し、`http://127.0.0.1:4173/` を開く
- 既にサーバーが動いている場合、**HTTP 200 が返ることを起動成功の根拠にしない。** 依存更新のあとは、稼働中のサーバーが古い解決パスを掴んだままになっていることがある。error overlay と console を見て確認し、必要なら所有者と調整して再起動する
- ポートが埋まっているときは、まず既存サーバーの所有者を確認する。許可を得て別ポートで起動した場合は、実際に開いた URL と手順との差を報告に書く
- `src/main.tsx` の `setupDevMocks()` により、Tauri 外ではブラウザ用の mock IPC が自動注入される。UI 確認はまずこのブラウザモードで行う

## ブラウザ操作ツールの使い方

- UI 確認は現行の利用可能な skill へ routing する。具体的な skill 名や API は実行時のロスターと各 skill の `--help` を正本とする
- エージェント側で完結する反復確認には `browser-harness` を使う
- ユーザーと通常のブラウザ画面を共有しながら操作する場合は、そのランタイムで利用可能なら `claude-in-chrome` または Codex Chrome アドオンを使う。利用可能性はランタイムに依存するため、実行時に確認する
- ターミナルペインに隣接表示したい場合は、グローバルの「ブラウザ操作の選択」表に従い `terminal-browser` を使う。pane はユーザーが明示的に指示した時だけ作る
- 同じページ・同じセッションを開き直さず再利用して、選択状態やスクロール位置を保持する
- 要素特定はツールが提供する DOM / アクセシビリティのスナップショットを使い、見た目の判断にはスクリーンショットを併用する
- 観察と操作は分けて検証する。観察は DOM / アクセシビリティツリー / スクリーンショットで足りるが、操作を伴う確認は実際の状態遷移を読み戻して確かめる。実証できていないものは未確認として残し、pass にしない
- 同じ操作が続けて失敗したら繰り返さない。入力が届いているかを先に切り分けるか、利用可能な別経路へ切り替える。バックグラウンドのタブは入力を落とすことがあるので、ツール側の focus に関する案内を先に確認する

## 調整時の必須フロー

- 変更前に対象画面を表示し、どの要素を触るのかを実画面で特定する
- 変更後は同じ画面を再表示して、見た目の差分を必ず確認する
- UI 変更の説明では、どの画面をどの方法で確認したかを明記する

## 避けること

- UI の見た目をコードだけで推測して修正を確定しない
- まず Tauri アプリを立ち上げる前提で進めない。最初の確認はブラウザモードを優先する
