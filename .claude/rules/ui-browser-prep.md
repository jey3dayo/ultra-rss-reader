# UI ブラウザ確認ルール

## UI/UX 調整の開始手順

- UI の余白、配置、視覚状態を調整する時は、利用可能なら変更前にブラウザで対象画面を確認する。クラウドでは Playwright / ヘッドレス Chromium による操作とスクリーンショットも正式な確認手段とする
- 描画できない場合は、提供画像、既存コンポーネント、設計規約から問題と修正根拠を特定し、実装・DOM / 操作テスト・draft PR 作成を進める。未確認の見た目を確認済みとして扱わない
- ツールや依存関係が未導入なら、まず `CONTRIBUTING.md` のセットアップとクラウド検証手順を試す。失敗した場合はコマンド・原因・未実施範囲を記録し、進行可能な作業を続ける
- 対話用の開発サーバーは `mise run app:dev:browser` で起動し、`http://127.0.0.1:4173/` を開く。Playwright E2E は既存設定がサーバー起動を管理するため、`CONTRIBUTING.md` の手順に従う
- 既にサーバーが動いている場合、**HTTP 200 が返ることを起動成功の根拠にしない。** 依存更新のあとは、稼働中のサーバーが古い解決パスを掴んだままになっていることがある。error overlay と console を見て確認し、必要なら所有者と調整して再起動する
- ポートが埋まっているときは、まず既存サーバーの所有者を確認する。**自分が起動したプロセスなら PID を指定して停止してよい。それ以外は所有者と調整してからでなければ停止しない。** 進行中の UI 確認や未保存の状態を壊すため。調整がついたら `mise run app:dev:browser` を再起動する。この task に用意されているのは固定ポートでの起動だけなので、未記載のコマンドを推測して起動しない
- `src/main.tsx` の `setupDevMocks()` により、Tauri 外ではブラウザ用の mock IPC が自動注入される。UI 確認はまずこのブラウザモードで行う

## ブラウザ操作ツールの使い方

- UI 確認は利用可能なブラウザツール / skill、またはリポジトリの Playwright を使う。専用ツール / skill は必須ではない。skill の API はその説明、Playwright の実行方法は `CONTRIBUTING.md` と既存設定を正本とする
- 専用ツールを選ぶ場合は名前ではなく能力で判断する。「エージェント側で完結する反復確認ができるか」「ユーザーと通常のブラウザ画面を共有しながら操作できるか」「ターミナルペインに隣接表示できるか」のうち必要な能力を満たし、かつ実行時のロスターに実在するものを選ぶ
- 例(存在すれば、名前は例示であり必須ではない): エージェント単独の反復確認には `browser-harness` のようなツール、画面共有操作にはそのランタイムで利用可能な `claude-in-chrome` や Codex Chrome アドオンのようなツール、ターミナル隣接表示にはグローバルの「ブラウザ操作の選択」表にある `terminal-browser` のようなツール(pane はユーザーが明示的に指示した時だけ作る)
- 専用ツールがない場合はリポジトリの Playwright に切り替える。ブラウザの導入や起動も失敗した場合は描画確認を未実施として残し、実装・自動検証・draft PR 作成を続ける。未記載の API を推測して呼び出さない
- 同じページ・同じセッションを開き直さず再利用して、選択状態やスクロール位置を保持する
- 要素特定は DOM / アクセシビリティのスナップショットや Playwright の role / label locator を使い、見た目の判断にはスクリーンショットを併用する
- 観察と操作は分けて検証する。観察は DOM / アクセシビリティツリー / スクリーンショットで足りるが、操作を伴う確認は実際の状態遷移を読み戻して確かめる。実証できていないものは未確認として残し、pass にしない
- 同じ操作が続けて失敗したら繰り返さない。入力が届いているかを先に切り分けるか、利用可能な別経路へ切り替える。バックグラウンドのタブは入力を落とすことがあるので、ツール側の focus に関する案内を先に確認する
- **バックグラウンドのタブではアニメーションの時計も止まる。** `document.visibilityState` が `hidden` のとき、transition は生成されても `currentTime` が 0 のまま進まず、計算値は開始値のまま動かない。これを「補間されない」「この環境では動かない」の根拠にしない。モーションを測る前に `visibilityState` を確認し、`getAnimations()` の `currentTime` を手で進めるか、中間値を静的に当てて描画する。タイマー（`setTimeout`）は止まりはしないがスロットリングされるので、経過時間の実測値も信用しない

## 調整時の必須フロー

- 描画可能なら変更前後に同じ対象画面を確認する。表示幅、折り返し、フォーカス、状態遷移など、変更に関係する項目を検証する
- 描画不能なら修正根拠と DOM / 操作テストの結果を記録し、未確認項目を draft PR に残す
- UI 変更の説明では対象画面、確認方法、実行結果を記載する。自動テスト、ブラウザ描画、ネイティブ実機の確認を区別し、失敗・未実施と理由も明記する
- レイアウト変更の描画確認や Keychain 動作の macOS 実機確認は、レビュー / マージ判断に必要な確認項目として残す。実装着手や draft PR 作成の前提にはしない
- browser-mode の mock IPC や jsdom テストの成功を、OS の認証プロンプトやネイティブ WebView 動作の保証にしない

## 避けること

- コードだけの推測や DOM テストだけで、見た目を検証済みと報告しない
- まず Tauri アプリを立ち上げる前提で進めない。最初の確認はブラウザモードを優先する
