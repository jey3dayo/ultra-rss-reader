# UI デザインレビュー反復ルール

## 対象

- UI 実装、UI 修正、見た目に影響するフロントエンド変更全般

## 完了前の必須フロー

1. 対象画面、変更の前後、関連する viewport と状態を定める
2. 次の観点それぞれについて pass / finding / N/A と短い根拠を記録する。N/A は理由を付ける。確認できなかったものを pass にしない
   - `DESIGN.md` との整合
   - 情報階層
   - 余白と視線誘導
   - 状態の分かりやすさと操作導線
   - 文言
   - レスポンシブ崩れ
   - 変更に関わるアクセシビリティ
3. 各 finding に対象、再現条件、証拠、必要な修正を記録し、**必須修正**と**承認済みの許容事項(accepted risk)**を分ける。根拠の無い好みを必須修正に変えない
4. 必須修正を直した範囲を再確認する。非軽微な外部共有の前には既存 DoD の独立レビューも行う。ループ回数と停止条件は既存 DoD に従う(指摘対応は最大 3 回、権限・認証・情報不足による停止条件を含む)。無限ループにしない
5. 完了条件は次のすべてを満たすこと
   - 必須観点をすべて確認済み
   - 未解消の must-fix が残っていない
   - accepted risk には理由・owner・必要な追跡先が付いている
   未確認や未解消がある場合は「完了」ではなく部分完了として明示する

## 実務上の基準

- 見た目の評価はコードだけで済ませず、可能な限り実画面で確認する
- UI 変更の完了報告では、どの観点を pass / finding / N/A と判定したか、必須修正の対応状況を短く添える
- 制約や既存仕様の都合で直しきれない finding は、accepted risk として理由・owner・残課題を明示する
